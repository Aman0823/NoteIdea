## Purpose

规定本地 SQLite 状态库的职责边界与容错行为：它只承载可从 markdown 重建的派生数据和运行时状态，任何情况下损坏或删除都不得导致用户写下的内容丢失。

## ADDED Requirements

### Requirement: 数据库职责边界

数据库只允许存放三类数据：索引缓存、运行状态、窗口状态。判据是随时删库重扫，用户不应感到丢失了任何自己写下的东西。

#### Scenario: 存放提醒配置
- **WHEN** 一条待办设置了提醒时间与重复规则
- **THEN** 这些配置写入 markdown 行内标记作为真源，数据库仅存其解析后的索引副本用于调度查询

#### Scenario: 存放提醒运行状态
- **WHEN** 某条提醒被触发或被用户推迟
- **THEN** 触发时间与推迟至时间写入数据库，markdown 文件不因此产生任何变更

#### Scenario: 存放便签位置
- **WHEN** 用户拖动便签窗口或调整其尺寸
- **THEN** 位置、尺寸、所属显示器写入数据库，不写入 markdown

#### Scenario: 尝试存放仅数据库可见的用户数据
- **WHEN** 某项用户输入的内容没有对应的 markdown 落点
- **THEN** 该设计不被接受，必须先确定其 markdown 表示

### Requirement: 数据库损坏容错

数据库文件可能因断电、磁盘错误而损坏。

#### Scenario: 启动时检测到数据库损坏
- **WHEN** 应用启动时完整性检查失败
- **THEN** 将损坏文件重命名保留，创建新库并全量重扫 vault 重建索引，不向用户报错阻塞启动

#### Scenario: 数据库文件不存在
- **WHEN** 应用启动时数据库文件不存在
- **THEN** 创建新库并全量重扫 vault 重建索引

#### Scenario: 数据库 schema 版本不匹配
- **WHEN** 数据库存在但 schema 版本低于当前应用期望
- **THEN** 执行迁移；迁移失败时按损坏处理，重建而非崩溃

### Requirement: 写入事务一致性

markdown 写盘与数据库更新必须保持一致，不得出现一方成功另一方失败的中间态。

#### Scenario: markdown 写盘成功
- **WHEN** actor 成功将 ChangeSet 落盘
- **THEN** 对应的数据库更新（删除队列记录、更新索引）在同一事务内提交

#### Scenario: markdown 写盘失败
- **WHEN** actor 写盘失败
- **THEN** 数据库事务回滚，队列记录保留，不出现「队列已清空但文件未改」的状态

### Requirement: 单进程独占访问

两个应用进程同时写同一个数据库会破坏单写者保证。

#### Scenario: 第二个实例尝试打开同一数据库
- **WHEN** 已有实例正在运行，另一个进程尝试打开同一个数据库文件
- **THEN** 第二个进程不获得写权限，交由单实例机制将用户意图转交给已有实例
