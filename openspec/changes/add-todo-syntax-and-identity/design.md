# Design

## D1 解析器只有 Rust 一份实现，前端通过 command 调用

速记条要边敲边决定弹什么层，Rust 侧扫描 vault 建索引也要独立解析，两处都需要这个能力。

**选定**：Rust 唯一实现，前端 `invoke('parse_todo_line', { text, cursor })`。

**否决 TS + Rust 各一套、共享 golden fixtures**：3.4 的规则（行尾右向左扫描、遇首个非法 token 停止、引号内屏蔽）恰恰是最容易两边写出细微差异的那类逻辑，而差异的表现是「前端弹层弹了但索引没认出来」这种极难归因的 bug。共享测试用例只能发现已经想到的分歧，想不到的那些正是要命的。

**否决 Rust 编译成 WASM 给前端**：能同时拿到单一真源和零 IPC，但要引入 wasm-pack / wasm-bindgen 构建链。当前项目的构建链干净到 `scripts/gen-icons.mjs` 都不用第三方依赖，为省几毫秒 IPC 换来一层 Windows 上易碎的工具依赖，不划算。真到 CM6 编辑器里发现 IPC 撑不住逐字符渲染，再切 WASM 也不用改接口形状。

**代价与对策**：每次需要解析都要一次 IPC 往返。对策见 D2。

## D2 解析请求不是「每键一次」，且必须可取消

**选定**：只在两种时机 invoke —— 光标左侧刚敲入的字符属于触发集合（`@ ! # ^`），或弹层已打开且用户在继续输入过滤词。普通打字不触发解析。

追加两条硬约束：

- 请求带序号，只接受最新一次的响应；过期响应直接丢弃。否则快速打字时旧响应会盖掉新状态，表现为弹层内容对不上当前输入
- 输入框的按键处理**绝不等待**解析结果。字符先进 input，弹层是异步补上来的。解析慢、解析失败、后端不可用，用户照样能把字打完并回车

**否决「每键 invoke，前端 await 后再决定是否插入字符」**：这会把 IPC 延迟直接摊到每一次按键上。速记条是这个软件的成败点（NFR-2），让它的打字手感取决于一条 IPC 链路，是拿核心体验去赌一个可以规避的风险。

## D3 解析器返回完整 token 列表，不返回「该弹什么」

**选定**：`parse_todo_line` 返回结构化结果 —— 正文 span、每个已识别标记的种类/取值/字节区间、每个非法降级 token 的位置、以及光标当前落在哪个 token 内。「该不该弹层、弹哪个」由前端根据这份结果自己判断。

**否决返回「弹时间条 / 弹标签列表 / 不弹」这种指令式结果**：同一份解析结果有三个消费方 —— 速记条弹层、CM6 的 chip 渲染（3.5）、索引扫描。把 UI 决策烤进解析器返回值，另两个消费方就得从指令里反推事实。解析器应该只回答「这行是什么」。

## D4 时间求值是独立一步，解析保持纯函数

3.2 的省略规则里有两条依赖当前时间：`@18:00` 指今天，已过则指明天；`@today` / `@tomorrow` 需要今天是哪天。

**选定**：解析器只返回未求值的时间表达式（原样的 `18:00` / `today 20:00` / `2026-08-14`）。另有一个求值函数，显式接收「当前时刻」作为参数，产出绝对时间。

**否决在解析器内部直接调 `Local::now()` 求值**：解析器会变成不纯函数，所有涉及时间的测试都要打时钟桩，而「已过则指明天」这个边界正好是最需要精确测试的地方 —— 得能构造「现在是 17:59」和「现在是 18:01」两种输入。让时间从参数进来，这类测试就是普通的表驱动用例。

顺带的好处：错过补发（FR-15）要按「当时的时间」重算，求值函数接收时刻参数天然支持这件事。

## D5 时间解析自己写，不引入 chrono

需要处理的输入形态是封闭的：`YYYY-MM-DD HH:MM` / `YYYY-MM-DD` / `today HH:MM` / `tomorrow` / `HH:MM`。

**选定**：自己写，用标准库 + 已有依赖处理日期算术。

**否决引入 chrono**：它解决的是时区数据库、跨时区换算、格式化本地化这些问题，而这一期只需要「本地时间的年月日时分」和「加一天」。FR-18 提到时区与夏令时变更需重算调度 —— 那是提醒引擎那一期的事，届时如果确实需要 tz 数据库再引入，接口不会因此改变（求值函数已经把时刻作为参数收进来了）。

## D6 `~id` 分配后立即经 actor 写回 md

3.6 定了分配时机是「首次需要被外部稳定引用时」（设提醒 / 贴屏）。剩下的问题是写盘时机。

**选定**：分配的同一个逻辑步骤内提交 `replace_line` 写回，写盘失败则该次「设提醒 / 贴屏」操作整体失败，DB 不留记录。

**否决「先在 DB 记下 ID，等该行下次有其他改动时搭车写入 md」**：中间态是 DB 里有一条引用不到 md 的记录。如果此时用户在 VS Code 里改了这一行，或者进程崩了，这条记录就永久失联 —— 而它承载的是提醒状态，失联意味着漏发提醒。漏发是提醒工具最坏的失败方向（FR-14a 已按这个原则定过一次）。

这一条也是 `replace_line` 的第一个真实调用方，`add-write-actor` 里已就绪的逻辑借此接上。

## D7 ID 生成：随机短哈希 + 全库查重，冲突则扩位

**选定**：4 位十六进制起（`~a3f9`），生成时在 `todos` 表查重，撞了重新生成；连续撞满若干次则扩到 5 位、6 位，上限 8 位。

**否决 `hash(路径 + 正文)`**：3.6 已否决过 —— 改一个字就换身份，「已触发」记录随之丢失，重复提醒会重放；移动文件即失联。

**否决自增整数**：从两个 vault 之间复制粘贴待办时必然撞号，而且 `~1` `~2` 这种 ID 在外部编辑器里看到会诱使用户手改。随机短哈希看着就不像该手动编辑的东西。

3.6 的重复 ID 处理照抄执行：粘贴导致同一 ID 出现在两处时，保留先扫到的那个，为后者重新分配。

## D8 无 ID 待办用「路径 + 行号 + 内容」三重校验定位

3.6 明确普通待办（既没提醒也没贴屏）不写 ID，保持 md 干净。这类待办在聚合视图里被勾选时需要定位。

**选定**：请求携带文件路径、行号、以及该行当前完整内容。actor 侧行号与内容都对得上才写；不匹配则拒绝，前端刷新索引后重试。

这与 `vault/file-write` 已有的基线冲突检测是同一机制（哈希不匹配则按内容重定位，多处匹配则拒绝而不猜测），不新增语义，只是明确了无 ID 待办依赖它。

## D9 引号字面量在扫描前先屏蔽

3.4 规则 1：引号内的标记字符一律是字面量。

**选定**：扫描元数据区之前先做一遍引号配对，把引号内区间标记为「不可解析」，右向左扫描时跳过这些区间。未闭合的引号视为普通字符，不屏蔽任何东西。

**否决在扫描时逐字符判断是否处于引号内**：右向左扫描时无法知道当前位置左边是否有开引号，除非再往左看一遍 —— 等于做两趟，不如先做一趟明确的配对。

未闭合引号不报错、不屏蔽，是因为用户正在打字的中间态必然出现单个引号，此时不能让已有的解析结果突然失效导致 chip 闪烁。

## D10 索引全量扫描在后台进行，不阻塞启动

**选定**：`setup()` 里 actor 就绪后 spawn 一个后台 task 做全量扫描，主窗口与速记条不等它。扫描中若用户已经触发速记，写入照常（速记走 append，与索引无关）。

**否决同步扫完再显示窗口**：vault 到几千篇（FR-5 假设的量级）时会明显拖慢启动，而托盘常驻应用的启动慢直接被感知为「这软件很重」。

需要向前端暴露索引就绪状态：依赖索引的界面（聚合视图，下一期）在未就绪时显示扫描进度而不是空列表 —— 空列表会被误读为「我的待办丢了」。

## Risks

- **速记条的弹层是这一期唯一的交互验证载体**。单行 input 上的弹层与 CM6 里的弹层在定位、键盘事件、失焦处理上并不完全一样，速记条上跑通不等于编辑器里能直接复用。对策：把弹层做成不依赖宿主元素类型的组件（只接收「锚点坐标 + 当前过滤词」），宿主适配层单独一层薄的
- **`~id` 是应用第一次主动改写用户手写的 md 行**。之前所有写入都是追加。哪怕只多一个空格或改了换行符，用户在 git diff 里看到的就是「这软件动了我的文件」。对策：ID 回写必须有专门的测试断言该行其余字节与文件其余内容逐字节不变
- **索引与 md 不一致的窗口客观存在**（这期没有文件监听）。用户在 VS Code 改了 md，应用这边索引是旧的。对策：这期就把「以 md 为准、索引随时可弃」写进 spec，并提供手动重扫入口；不要让任何逻辑把索引当作真源

## Open Questions

1. 弹层的键盘导航细节（上下键选择、Tab 是否确认、输入过滤词时的匹配算法）—— 实现时按最常见约定先做一版，用起来不顺手再调，不影响 spec
2. 标签弹层里已有标签的排序策略（按使用频次 / 最近使用 / 字典序）—— 需要真实数据才知道哪种顺手，先按使用频次
