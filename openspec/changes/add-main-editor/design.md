## Context

编辑器是 D16 选定的 CM6 + decoration 方案的第一次落地。它同时是 3.9 写入通道的第一个「任意变更」写者——此前所有写者提交的都是行级操作，编辑器不是。

两条不可让的既有约束贯穿全篇：

- **D17 规则二**：没有任何写者可以提交全文。编辑器也不例外
- **文本是真源，chip 只是叠加的渲染层**（D16 选 CM6 而非 ProseMirror 的全部理由）。渲染层任何时候都不得改写它渲染的文本

## Decisions

### E1 编辑器按字符偏移提交 `apply_edits`，不折叠成行区间

新增 `Operation::ApplyEdits { edits: Vec<Edit> }`，`Edit` 为 `{ from: usize, to: usize, insert: String }`，偏移相对 `base_hash` 所指的那份文档内容。actor 校验哈希严格相等后，按 `from` 降序依次应用。

**否决：`ReplaceRange { start_line, end_line, old_text, new_text }`（行区间替换）。**
它能复用现有 `replace_line` 的「按内容重定位」逻辑，不需要 rebase，实现便宜。但用户在第 1 行和第 900 行各改一处时，折叠出的区间会包含中间 898 行未改内容，payload 事实上退化为全文——那正是 D17 规则二要禁止的形状。虽然 `old_text` 校验能挡住静默吞写，但「看起来像行级、实际是全文」的 op 会诱使后续写者滥用。

**否决：编辑器用 `ReplaceFile`。** 直接违反 D17 规则二，不再论证。

**否决：一个 ChangeSet 携带多个不相交行区间。** 这等于在行的坐标系里重新发明字符偏移，还多一层折叠逻辑，且 3.9 原文写明主编辑器的定位方式是「字符偏移（CM6 原生）」。

代价（接受）：需要写一层「actor 广播的 Rust op → CM6 `ChangeSet`」的转换，否则前端 rebase 无从下手。见 E3。

### E2 `apply_edits` 的基线必须严格匹配，不重定位

现有 `vault/file-write` 的「基线已变但目标行可定位 → 按内容匹配位置执行」只对 `replace_line` 成立，因为它携带了整行原文可供搜索。字符偏移没有这种冗余信息：磁盘上多插了一行，所有偏移就整体错位，按错位偏移写下去是静默的数据损坏。

所以 `apply_edits` 的语义是二值的：哈希一致则应用，不一致则拒绝并回报当前磁盘内容的哈希，让前端 rebase 后重投。

**否决：让 actor 侧自己做 rebase。** actor 不知道前端那份文档的历史，没有 map 变更的依据。CM6 的 `ChangeSet.map()` 只存在于前端。

**否决：不一致时整篇重载磁盘版本。** 会丢掉用户在 debounce 窗口里刚敲的字。宁可可见地失败，也不静默改坏数据——这里连失败都不该有，rebase 是有正确解的。

### E3 远端变更转成 CM6 ChangeSet 后参与 rebase，但不进撤销栈

actor 落盘成功后广播 op。编辑器收到后：

1. 把 op 转成本文档坐标系下的 CM6 `ChangeSet`（`replace_line` 需要行号 → 字符偏移的换算；`append` 是末尾插入；`apply_edits` 直接对应）
2. 若这个 op 就是本窗口刚提交的那一批（按提交时记的 id 比对），标记为已确认，从「未确认变更」里移除
3. 否则视为远端变更：`dispatch` 应用它，并用 `unconfirmed.map(remote)` 重映射本地未确认变更

事务上带 annotation 标记为 remote，配 `addToHistory: false`，使远端变更不进本窗口 history——这就是 D20「每个窗口只能撤销自己产生的变更」的落地方式。

**否决：让远端变更也进撤销栈。** D20 已论证过：随手 Ctrl+Z 撤销掉 10 秒前便签上那下勾选，行为莫名且极难排查。

### E4 chip 渲染靠「行文本 → 解析结果」缓存，异步填充

CM6 的 `DecorationSet` 必须在 `update` 里同步算出来，而解析器只有 Rust 一份、只能异步 invoke。这两件事对不上。

解法：ViewPlugin 维护一个 `Map<行文本, TodoLine>` 缓存（解析是纯函数，行文本相同结果必然相同，所以行文本本身就是合法的缓存键）。

- 打开文件时一次批量 `parse_todo_lines(lines)` 填满缓存（新增批量 command，避免开一篇几百行的笔记打几百次 invoke）
- `update` 时对可见范围内的行查缓存：命中则生成 chip decoration，未命中则这一轮不渲染 chip，同时把该行文本排进异步解析队列
- 解析结果回来后 `dispatch` 一个空变更携带 effect，触发重算 decoration

代价：一行刚被改完的瞬间可能有一两帧还是原始语法。但这恰好与「光标所在行显示原始语法」重合——用户正在编辑的那一行本来就不渲染 chip，延迟只影响刚离开的行，肉眼几乎不可见。

**否决：前端自己写一个轻量 tokenizer 供同步渲染用。** 这就是「解析器两份实现」，`add-todo-syntax-and-identity` 已明确否决过（右向左扫描与引号屏蔽最易出细微差异），不因为换了个消费方就重开。

**否决：把解析结果做成 CM6 的 `StateField`，随文档变更同步推进。** 同步推进就要求同步解析，绕回上一条。

### E5 chip 的显示文案在前端格式化，写回一律走 Rust 序列化

`@2026-08-14 18:00` 显示成 `📅 8月14日 18:00`，这层格式化放前端。理由：它不是语法规则，是纯展示；写错了只影响一个 chip 的字样，不会污染文件；放 Rust 要为每个 chip 多一轮 invoke。

**但边界必须写死**：任何进入文档的文本都由 Rust 序列化产出。前端不得因为「已经会格式化了」就顺手拼回写文本——展示格式化和序列化是两个方向，只有后者会落盘。

### E6 光标所在行不渲染，判据是选区与行的相交

Typora 式的「光标所在行显示原始语法、离开即渲染」实现为：decoration 生成时跳过与当前选区相交的那些行。选区变化会触发 `update`，重算即可。

多选区、跨行选中时，所有被选区触及的行都显示原始语法。这比「只看主光标」更符合直觉：用户框选一段要改，不该有 chip 在里面挡着。

**否决：用 `Decoration.replace` 的 `inclusive` 配合光标进入自动展开。** CM6 的 atomic range 在光标经过时是跳过而非展开，做不出「进入即展开」的效果，还会让方向键行为变怪。

### E7 复选框点击与 chip 编辑都走编辑缓冲，不另开写路径

点复选框、在 chip 上改时间，都 `dispatch` 一个本地 change 进编辑缓冲，然后立即 flush 落盘（不等 800ms——这两个是明确的动作，不是打字）。

**否决：这两个操作直接调 `replace_line` command 绕过缓冲。** 同一行会同时存在「缓冲里的版本」和「刚被 actor 改过的磁盘版本」，然后靠广播回流把缓冲拉回来。多一条写路径就多一类竞态，而收益只是省掉一次缓冲更新。

### E8 切换笔记与关窗前强制落盘，落盘失败则不切换

FR-4 要求切换笔记、失焦、退出时立即写盘。若这次写盘失败（权限、磁盘满），**不得继续切换**：切走之后那份缓冲就没有承载它的界面了，用户的输入会静默消失。失败时留在当前笔记，把失败原因显示出来（复用现有写入失败列表的通道）。

### E9 文件树是一次性列表 + 手动刷新，不做 watcher

新增 `list_notes` command 返回 vault 内 md 的目录树（跳过 `.noteidea/`、`assets/`）。打开时拉一次，新建文件后重拉，另给一个手动刷新。

外部新增的文件不会自动出现——这一期没有 watcher，这是已知且明说的限制，不假装同步。

### E10 CM6 只进主窗口打包入口

`quick.ts`（速记条）与 `time-picker.ts` 不得 import 任何 CM6 模块。速记条的首帧可输入时间是 NFR-2 定的成败线（已实测 p95 18-30ms），编辑器的体积绝不能进那条路径。Vite 多入口天然分包，但要在收尾时确认产物里 quick 的 chunk 没有引入 CM6。

## Risks

- **decoration 架构定错要重写 chip、输入辅助、复选框三处**。这是本期唯一的架构性风险，E4/E6/E7 三条就是为了把它钉住。判据：如果实现中发现需要「让渲染层改写文本」才能做到某个效果，说明架构错了，停下来重新想
- **rebase 路径难以自然触发**：本期只有编辑器和速记条两个写者，且速记条只写 `inbox.md`。要主动构造测试（在 VS Code 里改文件、或用速记条往正在编辑的 `inbox.md` 里追加）才能验到 E2/E3，否则这段代码到有便签那期才第一次真跑
- **`identity.rs` 接进编译后可能大面积报错**：它从未编译过，里面调用的 `write_marker_to_line` 也不存在。要按「先补序列化、再接编译、再跑测试」的顺序，不要一次全推
